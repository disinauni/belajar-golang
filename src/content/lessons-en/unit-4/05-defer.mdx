# Defer

Imagine you open a file, and partway through the function there are several different `return` paths (success, error, etc.). On every one of those paths, you have to remember to close that file — easy to forget, and an easy source of bugs. Go has an elegant solution: `defer`.

## Defer Basics

```go
package main

import "fmt"

func main() {
    fmt.Println("Start")
    defer fmt.Println("Done (deferred)")
    fmt.Println("Middle")
}
```

Output:
```
Start
Middle
Done (deferred)
```

## Breaking Down Defer

**`defer fmt.Println("Done (deferred)")`** — the `defer` keyword postpones this call to `fmt.Println(...)` until the **currently running function** (`main` here) is truly about to finish (right before it actually returns to its caller) — **not** until the end of the nearest block of code.

Notice the output order: even though `defer` is written as the **second** line, it prints **last** — after `"Middle"`. The statement below it (`fmt.Println("Middle")`) still runs first as normal, and only after `main()` is otherwise done does the deferred statement run.

Think of `defer` like sticking a note on the door that says "turn off the lights before you leave" — you keep working as usual, but that note **will** be seen and acted on right before you actually leave the room.

## LIFO Order for Multiple Defers

```go
package main

import "fmt"

func main() {
    defer fmt.Println("One")
    defer fmt.Println("Two")
    defer fmt.Println("Three")
    fmt.Println("Main function running")
}
```

Output:
```
Main function running
Three
Two
One
```

When there are **multiple** `defer` statements in one function, they execute in **LIFO** order (*Last In, First Out*) — the one deferred **most recently** runs **first**. Just like a stack of plates: the last plate you put on top is the first one you pick back up.

:::note
Remember the order with a stack analogy: `defer` pushes a task onto the top of a stack, and when the function finishes, that stack gets "unwound" from the top down — so the last one in is the first one out.
:::

## Gotcha: Arguments Are Evaluated Now, Not Later

```go
package main

import "fmt"

func main() {
    i := 0
    defer fmt.Println("value of i when defer was created:", i)
    i = 100
    fmt.Println("value of i now:", i)
}
```

Output:
```
value of i now: 100
value of i when defer was created: 0
```

This often surprises beginners: the **arguments** of a deferred statement are evaluated **the moment that `defer` line executes**, not when the call is actually run later. So `i`'s value gets "photographed" (`0`) right when `defer` is written — even though `i` is later changed to `100`, the postponed `fmt.Println` call still uses that "frozen" `0` value.

:::warning
Only the **function call itself** is postponed (when it actually runs), not the **evaluation of its arguments**. If you need the *current* value at the moment the defer actually runs, wrap it in an anonymous function: `defer func() { fmt.Println(i) }()` — we'll dig deeper into this in the upcoming **Closures** lesson.
:::

## Common Use: Cleanup

The most common pattern for `defer` is making sure a resource gets "cleaned up" no matter which path the function takes to end:

```go
func processData(valid bool) {
    fmt.Println("Opening connection...")
    defer fmt.Println("Closing connection.") // always runs, no matter the outcome

    if !valid {
        fmt.Println("Data is invalid, stopping here.")
        return // defer STILL runs even with an early return
    }
    fmt.Println("Processing data...")
}
```

No matter whether the function stops via a `return` in the middle or runs all the way to the end, the deferred statement is **always** executed — this is what makes `defer` so reliable for cleanup compared to manually placing "closing" code on every possible exit path.

## Common Mistakes

1. **Assuming defer runs immediately, in normal code order:**
   ```go
   defer fmt.Println("A")
   fmt.Println("B")
   // Output: B then A — not A then B!
   ```

2. **Assuming a defer's arguments are evaluated later, rather than when the defer statement is written:**
   ```go
   n := 5
   defer fmt.Println(n) // n is "photographed" now: its value is 5
   n = 10
   // When the function finishes, it still prints 5, not 10
   ```

3. **Placing a defer inside a loop for a resource that should be closed per-iteration:**
   ```go
   for i := 0; i < 1000; i++ {
       // defer openFile(...) here would pile up 1000 defers
       // and all of them would only run after the ENTIRE function finishes,
       // not at the end of each iteration — this can exhaust resources!
   }
   ```
   `defer` is always tied to the **function** that's currently running, not the nearest block of code (like a loop or an `if`).

## Summary

| Concept | Example |
|---|---|
| Postponing execution | `defer fmt.Println("done")` |
| Runs when | The surrounding function finishes (right before it actually returns) |
| Multiple-defer order | LIFO — deferred last, runs first |
| Argument evaluation | At the moment the defer line executes, not when it runs later |
| Common use | Cleanup (closing files, connections, etc.), closing messages |
