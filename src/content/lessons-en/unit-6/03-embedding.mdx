# Struct Embedding

Go **doesn't have** an inheritance concept like Java or C++. Instead, Go has **struct embedding** — a way to insert one struct into another so its fields and methods automatically "come along". This is Go's approach to *code reuse*: composition, not inheritance.

## Embedding a Struct

```go
package main

import "fmt"

type Animal struct {
    Name string
    Age  int
}

func (a Animal) Description() string {
    return fmt.Sprintf("%s (%d years old)", a.Name, a.Age)
}

type Dog struct {
    Animal
    Breed string
}

func main() {
    doggo := Dog{
        Animal: Animal{Name: "Rex", Age: 3},
        Breed:  "Golden Retriever",
    }

    fmt.Println(doggo.Name)
    fmt.Println(doggo.Description())
    fmt.Println(doggo.Breed)
}
```

Output:
```
Rex
Rex (3 years old)
Golden Retriever
```

## Breaking Down Struct Embedding

**`type Dog struct { Animal; Breed string }`** — notice `Animal` is written **without a field name**, just the type name alone. This is what's called an *embedded field*. This field automatically gets a name equal to its type name, `Animal`.

**`doggo.Name`** — even though `Name` is defined inside `Animal`, you can access it directly from `doggo` without writing `doggo.Animal.Name`. This is called **field promotion** — a field from the embedded struct "surfaces" onto the outer struct.

**`doggo.Description()`** — the same thing applies to methods too: `Description()` is defined for `Animal`, but can be called directly from `Dog`. This is **method promotion**.

Picture `Dog` like a box that has an `Animal` box inside it, with no label. Because there's no label, everything inside the `Animal` box feels like it "directly belongs" to the `Dog` box.

**`doggo.Animal.Name`** — the full path still exists and is still valid. Sometimes you need to write this explicitly, for example when field names collide (see Common Mistakes).

## Not Inheritance — This Is Composition

An important distinction: `Dog` doesn't **"become"** `Animal`. You can't treat `Dog` as `Animal` directly the way you'd *upcast* in classic object-oriented languages. What happens is `Dog` **has** an `Animal` inside it (a "has-a" relationship, not "is-a"), and Go simply makes it easier to access through promotion.

You can also **override** a promoted method by defining a method with the same name directly on the outer struct:

```go
func (d Dog) Description() string {
    return fmt.Sprintf("%s the %s", d.Name, d.Breed)
}
```

After this, `doggo.Description()` calls `Dog`'s version, not `Animal`'s anymore.

:::tip
Go's philosophy is often summarized as: *"prefer composition over inheritance"*. Struct embedding is how Go supports this philosophy without a special keyword like `extends`.
:::

:::note
Embedding isn't limited to structs — you can also embed an interface into another struct or interface. We'll touch on this a little in the next lesson.
:::

## Common Mistakes

1. **Ambiguous field when two embedded structs share the same field name:**
   ```go
   type A struct{ Name string }
   type B struct{ Name string }
   type C struct {
       A
       B
   }

   func main() {
       c := C{A{"X"}, B{"Y"}}
       fmt.Println(c.Name) // ERROR: ambiguous selector c.Name
   }
   ```
   Go doesn't know whether `Name` refers to `A`'s or `B`'s — you must write it explicitly as `c.A.Name` or `c.B.Name`.

2. **Forgetting the embedded field's name when creating a struct literal:**
   ```go
   doggo := Dog{Name: "Rex"} // ERROR: unknown field 'Name' in struct literal of type Dog
   ```
   `Name` isn't a direct field of `Dog` — you must fill it in through `Animal`: `Dog{Animal: Animal{Name: "Rex"}}`.

## Summary

| Concept | Example |
|---|---|
| Embedded field | `type Dog struct { Animal; Breed string }` |
| Field promotion | `doggo.Name` (even though `Name` belongs to `Animal`) |
| Method promotion | `doggo.Description()` |
| Explicit access | `doggo.Animal.Name` |
| Overriding a method | Redefine a method with the same name on the outer struct |
