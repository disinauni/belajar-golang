# sync.WaitGroup & Mutex

We already learned `time.Sleep` as a temporary crutch for waiting on goroutines — but that's just a rough guess. Now it's time to learn the real tools: **`sync.WaitGroup`** for reliably waiting until many goroutines are finished, and **`sync.Mutex`** for protecting data that's accessed by many goroutines at once.

Picture a `WaitGroup` like a teacher counting how many students are still outside the classroom — once every student is inside (`Done`), the lesson starts (`Wait` returns). Meanwhile, `Mutex` is like the lock on a public restroom — only one person is allowed in (`Lock`) until they come out (`Unlock`), so there's no crowding.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    var mu sync.Mutex
    total := 0

    for i := 1; i <= 5; i++ {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            mu.Lock()
            total += n
            mu.Unlock()
        }(i)
    }

    wg.Wait()
    fmt.Println("Total:", total)
}
```

Output:

```
Total: 15
```

## Breaking Down the Concept

### `sync.WaitGroup`: Waiting for Many Goroutines

```go
var wg sync.WaitGroup

wg.Add(1)   // "add one goroutine to wait for"
go func() {
    defer wg.Done() // "this goroutine is finished"
}()

wg.Wait()   // "wait until every goroutine that was Add()ed has called Done()"
```

`WaitGroup`'s three main methods:
- **`Add(n)`** — increases the **count** of goroutines to wait for (usually called before `go func()`, with `n = 1` per goroutine).
- **`Done()`** — decreases the count by 1, signaling "this goroutine is finished." Usually called with `defer` right at the start of the goroutine, so it's guaranteed to run even if something goes wrong along the way.
- **`Wait()`** — blocks until the count returns to **0** (every goroutine has called `Done()`).

:::tip
Always call `wg.Add(1)` **before** `go func() { ... }()`, never inside the goroutine itself. If `Add` is called inside the goroutine, there's a chance `wg.Wait()` in `main()` could already pass before `Add` even gets called — a race condition on the `WaitGroup` itself!
:::

### Race Conditions: The Problem Mutex Solves

Imagine, **without** a `Mutex`, many goroutines running `total += n` at the same time. The operation `total += n` actually consists of 3 steps: read `total`, add `n`, write the result back into `total`. If two goroutines do this **at the same time**, one of the additions can get "overwritten" and lost — this is a **race condition**, a bug that makes a program's result inconsistent (sometimes correct, sometimes wrong, depending on timing).

### `sync.Mutex`: A Lock for Shared Data

```go
var mu sync.Mutex

mu.Lock()
total += n // only one goroutine may be here at a time
mu.Unlock()
```

- **`Lock()`** — "locks" access. If another goroutine already holds the lock, this goroutine **blocks** and waits until it's released.
- **`Unlock()`** — releases the lock, letting another waiting goroutine in.

The code between `Lock()` and `Unlock()` is called the *critical section* — the part that only **one goroutine** may run at a time.

### The `defer mu.Unlock()` Pattern

```go
func addSafely(mu *sync.Mutex, total *int, n int) {
    mu.Lock()
    defer mu.Unlock() // guaranteed to run, even if there's a panic mid-function
    *total += n
}
```

Calling `Unlock()` via `defer` right after `Lock()` is a strongly recommended habit — it guarantees the lock is **always** released, even if there's an early `return` or a panic somewhere in the function. Forgetting `Unlock()` means other goroutines will wait **forever** for a lock that's never released (deadlock).

:::warning
If you forget `Unlock()` entirely, every other goroutine calling `Lock()` on the same mutex will block **forever**. Always make sure every `Lock()` has its matching `Unlock()` — the habit of `defer mu.Unlock()` right after `Lock()` is the safest way to guarantee this.
:::

## Common Mistakes

1. **Race condition: forgetting to use a Mutex for shared data:**
   ```go
   var wg sync.WaitGroup
   total := 0
   for i := 1; i <= 100; i++ {
       wg.Add(1)
       go func(n int) {
           defer wg.Done()
           total += n // BUG: race condition! Many goroutines write
           // to total at the same time without Mutex protection.
       }(i)
   }
   wg.Wait()
   fmt.Println(total) // the result is UNPREDICTABLE, often < 5050
   ```
   Without a `Mutex` (or a channel instead), `total += n` performed by many goroutines simultaneously can overwrite each other and lose results.

2. **Calling Add() inside the goroutine instead of before go func():**
   ```go
   var wg sync.WaitGroup
   for i := 0; i < 3; i++ {
       go func() {
           wg.Add(1) // BUG: race — wg.Wait() below might already have
           // finished before this Add() even gets called!
           defer wg.Done()
           // ...
       }()
   }
   wg.Wait()
   ```
   `Add()` must be called by the **calling** goroutine (usually `main`), before `go func()` runs — so the count is already correct before `Wait()` starts checking it.

3. **Forgetting Unlock(), causing a deadlock:**
   ```go
   mu.Lock()
   if errorCondition {
       return // BUG: the Unlock() below never runs if we
       // return here, the mutex stays locked forever!
   }
   mu.Unlock()
   ```
   The fix: use `defer mu.Unlock()` right after `mu.Lock()`, so the lock is guaranteed to be released no matter which exit path the function takes.

## Summary

| Concept | Example |
|---|---|
| Declaring a WaitGroup | `var wg sync.WaitGroup` |
| Increment count before a goroutine | `wg.Add(1)` |
| Mark a goroutine finished | `defer wg.Done()` |
| Wait for all goroutines to finish | `wg.Wait()` |
| Declaring a Mutex | `var mu sync.Mutex` |
| Protect shared data | `mu.Lock()` ... `defer mu.Unlock()` |
| Problem without a Mutex | Race condition — inconsistent results |
