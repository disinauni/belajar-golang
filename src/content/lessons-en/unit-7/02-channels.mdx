# Channels

In the previous lesson we learned how to launch goroutines, but there's a problem: how does a goroutine "return" its work to `main()`, or communicate with another goroutine, **safely**? The answer: **channels**.

Picture a channel like a **mail pipe** between two rooms: one goroutine drops a letter (data) in at one end of the pipe, another goroutine picks it up from the other end. Go even has a famous philosophy about this: *"Don't communicate by sharing memory; share memory by communicating"* — don't share data by having many goroutines poke at the same variable, send data through a channel instead.

```go
package main

import "fmt"

func calculateSquare(n int, result chan int) {
    result <- n * n // send the result into the channel
}

func main() {
    ch := make(chan int) // create an int channel

    go calculateSquare(7, ch)

    value := <-ch // receive the result from the channel (blocks until data arrives)
    fmt.Println("Square result:", value)
}
```

Output:

```
Square result: 49
```

## Breaking Down the Concept

### Creating a Channel: `make(chan int)`

```go
ch := make(chan int)
```

`make(chan int)` creates a new channel of type `int` — meaning this channel can only send/receive `int` values. Channels, like slices and maps, are a reference type that must be created with `make` before use. You can make a channel of any type: `chan string`, `chan bool`, `chan float64`, even `chan []int`.

### Sending Data: `ch <- value`

```go
result <- n * n
```

The `<-` operator on the **right** of the channel name means **sending** a value into that channel. Read it as an arrow showing the direction data flows: the value "flows into" `result`.

### Receiving Data: `<-ch`

```go
value := <-ch
```

The `<-` operator on the **left** of the channel name (before the channel name) means **receiving** a value from that channel. The received value is stored into the `value` variable.

:::tip
An easy way to remember the direction of `<-`: the arrow always points **toward where the data is flowing**. `ch <- v` means "v flows into ch". `v := <-ch` means "a value from ch flows into v".
:::

### Blocking Behavior of Channels (Unbuffered)

This is the **most important** part to understand: a plain channel (created without capacity, called an *unbuffered channel*) is **blocking** on both sides:

- A send, `ch <- v`, will **block** until another goroutine is ready to receive from that channel.
- A receive, `v := <-ch`, will **block** until another goroutine sends something into that channel.

This is actually a feature, not a bug — this blocking behavior is exactly what makes channels useful for **synchronization**. In the example program above, the line `value := <-ch` in `main()` waits until the `calculateSquare` goroutine finishes computing and sends its result — no `time.Sleep` needed at all!

```go
ch := make(chan int)
go calculateSquare(7, ch)
value := <-ch // main() automatically waits here until data arrives
```

Compare this to the previous lesson, which needed `time.Sleep` to guess a duration — channels solve this elegantly: `main()` waits **exactly as long** as the goroutine needs, no more, no less.

:::note
A channel and a `nil` variable (not yet `make`'d) are different things! A channel that hasn't been created with `make` has the value `nil`, and sending/receiving on a `nil` channel will **block forever** (deadlock). Always make sure a channel has been `make`'d before you use it.
:::

## Common Mistakes

1. **Deadlock: receiving from a channel that will never be sent to:**
   ```go
   func main() {
       ch := make(chan int)
       value := <-ch // RUNTIME ERROR: fatal error: all goroutines are
       // asleep - deadlock! (no other goroutine is sending)
       fmt.Println(value)
   }
   ```
   Since no other goroutine ever sends to `ch`, `main()` waits forever — and the Go runtime detects this as a deadlock and stops the program with an error.

2. **Forgetting that channels block, expecting the code to run like normal:**
   ```go
   func main() {
       ch := make(chan int)
       ch <- 5 // BUG: blocks here, because there's no receiving
       // goroutine yet — main() is the only "thread" running,
       // so it's stuck waiting on itself!
       fmt.Println(<-ch)
   }
   ```
   Sending on an unbuffered channel from within the same goroutine, with no other receiver, deadlocks immediately — because there's no "other party" that could receive while `main()` itself is busy waiting on the send.

3. **Receiving from a channel twice when it was only sent to once:**
   ```go
   ch := make(chan int)
   go func() {
       ch <- 10
   }()
   a := <-ch
   b := <-ch // BUG: blocks forever, there's no second send!
   fmt.Println(a, b)
   ```
   Every channel needs to receive exactly as many sends as the number of receives performed — if they're unbalanced, one side will block forever.

## Summary

| Concept | Example |
|---|---|
| Creating a channel | `ch := make(chan int)` |
| Sending into a channel | `ch <- 42` |
| Receiving from a channel | `value := <-ch` |
| Unbuffered channel behavior | Blocks on both sides until a matching partner is ready |
| Synchronization without Sleep | Receiving from a channel = automatically waiting for the goroutine |

Unbuffered channels are useful, but sometimes we want a goroutine to be able to send a few values ahead of time **without** immediately waiting for a receiver to be ready. In the next lesson, we'll learn about **select** and **buffered channels** for exactly that.
