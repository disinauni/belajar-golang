# Select & Buffered Channels

In the previous lesson we learned about unbuffered channels, which always block until a partner is ready. Now we'll learn two more tools: **buffered channels** (channels with a "storage box" so they aren't always blocking) and **select** (waiting on multiple channels at once, like a `switch` but for channels).

Picture a buffered channel like a **mailbox** with a limited number of slots: you can drop letters in without waiting for the mail carrier to show up, as long as there's still room. `select`, meanwhile, is like a receptionist watching several phones at once — the moment one rings, they pick it up.

```go
package main

import "fmt"

func main() {
    ch := make(chan string, 2) // buffered channel, capacity 2

    ch <- "message 1" // doesn't block, buffer still has room
    ch <- "message 2" // doesn't block, last slot filled

    close(ch) // close the channel, no more sends allowed

    for msg := range ch {
        fmt.Println("Received:", msg)
    }
}
```

Output:

```
Received: message 1
Received: message 2
```

## Breaking Down the Concept

### Buffered Channels: `make(chan T, capacity)`

```go
ch := make(chan string, 2)
```

The second argument to `make` sets the channel's **buffer capacity**. This buffered channel can hold up to 2 values **without blocking**, even before any other goroutine is ready to receive.

- As long as the buffer **isn't full**, `ch <- v` **doesn't block** — it moves straight on to the next line.
- Once the buffer **is full**, `ch <- v` will **block** until a slot frees up (for example, because another goroutine receives from it).
- Receiving from an **empty** buffered channel still blocks, just like an unbuffered channel.

:::note
The unbuffered channel we learned about in the previous lesson is actually the same thing as a buffered channel with capacity 0 — `make(chan int)` is equivalent to `make(chan int, 0)`.
:::

### Closing a Channel: `close(ch)`

```go
close(ch)
```

`close` marks a channel as having **no more sends coming**. After closing:
- You can still **receive** every value that was already sitting in the buffer.
- Sending to an already-`close`d channel will **panic**.
- Receiving from a `close`d channel that is now empty immediately returns the **zero value**, rather than blocking.

### Detecting a Closed Channel: `v, ok := <-ch`

```go
v, ok := <-ch
if !ok {
    fmt.Println("Channel is closed and empty")
}
```

This two-value receive form tells you whether `v` was actually sent (`ok == true`) or whether the channel is closed and empty, meaning `v` is just a zero value (`ok == false`). This matters so you don't mistake a zero value for real data that was actually sent.

### `range` on a Channel

```go
for msg := range ch {
    fmt.Println("Received:", msg)
}
```

A `range` loop on a channel automatically receives values one by one until the channel is **closed and empty**, then the loop stops on its own. This is the most common way to read every value from a channel without manually checking `ok`.

### `select`: Waiting on Multiple Channels

```go
select {
case v1 := <-ch1:
    fmt.Println("From ch1:", v1)
case v2 := <-ch2:
    fmt.Println("From ch2:", v2)
default:
    fmt.Println("No channel is ready")
}
```

`select` waits on **multiple channels at once**, then runs the `case` for whichever channel is **ready first**. If several channels are ready at the same time, Go picks one **at random** (not in the order they're written). The `default` block (optional) runs immediately if **no** channel is ready at all — making `select` non-blocking.

:::tip
`select` without `default` blocks until one of its `case`s is ready — like waiting for whichever phone rings first. With `default`, `select` immediately "gives up" if all the channels are still quiet, which is great for non-blocking polling.
:::

## Common Mistakes

1. **A full buffer, but expecting no blocking:**
   ```go
   ch := make(chan int, 2)
   ch <- 1
   ch <- 2
   ch <- 3 // BUG: blocks! The capacity-2 buffer is already full,
   // and there's no other goroutine receiving.
   ```
   A buffered channel only delays blocking until the buffer fills up — it doesn't remove blocking behavior entirely.

2. **Sending to a channel that's already been closed:**
   ```go
   ch := make(chan int, 1)
   close(ch)
   ch <- 5 // RUNTIME ERROR: panic: send on closed channel
   ```
   After `close(ch)`, the channel can no longer accept sends — Go will panic if you force one.

3. **Forgetting that closing a channel twice panics:**
   ```go
   ch := make(chan int)
   close(ch)
   close(ch) // RUNTIME ERROR: panic: close of closed channel
   ```
   Only `close` a channel once, usually done by the **sending** goroutine (not the receiver), after all sends are finished.

## Summary

| Concept | Example |
|---|---|
| Buffered channel | `make(chan int, 3)` |
| Send without blocking (while there's room) | `ch <- v` |
| Close a channel | `close(ch)` |
| Read all values until closed | `for v := range ch { ... }` |
| Detect a closed channel | `v, ok := <-ch` |
| Wait on multiple channels | `select { case ... case ... default: ... }` |
