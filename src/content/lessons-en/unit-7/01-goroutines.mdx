# Goroutines

Up until now, every line of code in your programs has run **one at a time**, in order — line 1 finishes, then line 2 runs. Go has a signature feature that changes this whole way of thinking: **goroutines**. With a single word, `go`, you can tell Go to run a function **concurrently** — "in the background" — while the main program keeps going.

Picture yourself as a restaurant manager. Instead of cooking one order all the way through before starting the next, you have several cooks (goroutines) who can work on multiple orders at once. You (the `main` function) just hand out the tasks and move on to other work.

```go
package main

import (
    "fmt"
    "time"
)

func greet(name string) {
    fmt.Println("Hello from", name)
}

func main() {
    go greet("goroutine A")
    go greet("goroutine B")

    fmt.Println("main() running first...")
    time.Sleep(100 * time.Millisecond) // give the goroutines time to finish
    fmt.Println("main() done")
}
```

Output (the order of the two middle lines can swap, but the opening & closing lines always stay in place):

```
main() running first...
Hello from goroutine A
Hello from goroutine B
main() done
```

## Breaking Down the Concept

### The `go` Keyword

```go
go greet("goroutine A")
```

Putting `go` in front of a function call makes Go run that function as a new goroutine — **without waiting for it to finish**. The next line (`fmt.Println("main() running first...")`) executes immediately, even though `greet("goroutine A")` may not have printed anything yet.

Goroutines are **lightweight** — nothing like a heavy OS thread. A Go program can run thousands, even millions, of goroutines at once, because the Go runtime manages their scheduling itself (rather than the operating system doing it directly), with an initial stack of only about 2KB per goroutine.

### `main()` Doesn't Wait for Goroutines

This is the **single most important** point to understand early on:

```go
func main() {
    go greet("goroutine A")
    // main() does NOT stop here to wait for greet() to finish!
}
```

The moment `main()` reaches the end of its function and **returns**, the entire program stops immediately — including any goroutines that haven't finished yet, which are simply "cut off" mid-flight without any warning. That's why the example above uses `time.Sleep(100 * time.Millisecond)` — so `main()` gives the goroutines enough time to finish before the program ends.

:::warning
`time.Sleep` is only a **temporary**, unreliable way to wait for a goroutine — we're essentially guessing how long the goroutine will take. The correct, guaranteed way is `sync.WaitGroup`, which we'll cover in Lesson 4. Think of `time.Sleep` in this lesson as a "temporary crutch" for learning the goroutine concept, not a production solution.
:::

### Concurrent Doesn't Always Mean Parallel

```go
go greet("goroutine A")
go greet("goroutine B")
```

These two goroutines are **concurrent** — the Go runtime may run them alternately or genuinely at the same time (depending on how many CPU cores are available). Because the scheduling is outside our control, **the order in which `goroutine A` and `goroutine B` print is not guaranteed** — sometimes A first, sometimes B first. This is normal in concurrency, and one of the reasons we need synchronization tools like channels (Lesson 2) and `sync.WaitGroup` (Lesson 4).

:::tip
Concurrent and parallel are different things! Concurrent means "managing many things at once" (can alternate on a single core), while parallel means "actually doing many things at the exact same time" (needs multiple cores). Goroutines enable both, depending on the environment running them.
:::

## Common Mistakes

1. **Forgetting to wait for a goroutine, so the program ends first:**
   ```go
   func main() {
       go fmt.Println("This message might never print!")
       // BUG: main() finishes immediately, the goroutine above might
       // never get a chance to run at all!
   }
   ```
   Without some way to wait (like a temporary `time.Sleep`, or the correct `sync.WaitGroup`), a goroutine can be "cut off" before it manages to do anything.

2. **Loop variable capture — the classic goroutine bug in Go:**
   ```go
   func main() {
       for i := 0; i < 3; i++ {
           go func() {
               fmt.Println(i) // BUG: most likely prints "3 3 3"!
           }()
       }
       time.Sleep(100 * time.Millisecond)
   }
   ```
   In the Go version this site uses (before Go 1.22), the loop variable `i` is **shared** across all iterations — it isn't copied fresh for each iteration. Because the new goroutine actually reads `i` later (possibly after the loop has already finished), all the goroutines can end up reading the same value of `i`, namely `3`.

   **The classic fix**: pass `i` as a *parameter* to the goroutine's closure, so each goroutine gets its own copy:
   ```go
   func main() {
       for i := 0; i < 3; i++ {
           go func(n int) {
               fmt.Println(n) // correct: prints 0, 1, 2 (the order between
               // goroutines can be random, but the values are guaranteed correct)
           }(i)
       }
       time.Sleep(100 * time.Millisecond)
   }
   ```
   By passing `i` as the argument `n`, the current value of `i` is immediately **copied** into that goroutine's own parameter `n` — so it no longer changes even as `i` keeps incrementing in the loop.

3. **Assuming a goroutine is guaranteed to finish first:**
   ```go
   go slowProcess()
   fmt.Println("Done!") // BUG: the goroutine isn't necessarily done yet
   ```
   `go` only "schedules" execution — it never guarantees completion order. Never assume anything about ordering without an explicit synchronization mechanism.

## Summary

| Concept | Example |
|---|---|
| Launching a goroutine | `go functionName(arguments)` |
| main() doesn't wait | goroutines get cut off if main() returns first |
| Temporary crutch | `time.Sleep(100 * time.Millisecond)` |
| Loop variable capture (bug) | `for i := 0; i < n; i++ { go func() { use(i) }() }` — wrong |
| Fix for loop variable capture | `for i := 0; i < n; i++ { go func(n int) { use(n) }(i) }` — correct |

Goroutines only become truly useful once there's a safe way for them to **communicate** and share results with each other. In the next lesson, we'll learn about **channels** — "pipes" that connect goroutines so they can safely send data to each other.
