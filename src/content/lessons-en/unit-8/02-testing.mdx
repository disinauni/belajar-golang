# Testing with go test

Imagine you have a `CalculateDiscount` function used in 50 different places across your application. One day you "fix" that function — except your fix actually breaks the logic for a certain case. Without automated tests, you only find out there's a bug after a user complains. With automated tests, you find out **before** the code ever gets deployed.

:::note
Real testing needs a separate file (`_test.go`) and the `go test` command — not `go run` — so it can't be run directly through this site's single-file playground. The `_test.go` code in this lesson is meant to be **read and understood**; the exercises at the end are still `package main` programs you can run.
:::

## Anatomy of a Test Function

Say you have this simple function in a file `math.go`:

```go
package math

func Add(a, b int) int {
    return a + b
}
```

Its test is written in a separate file called `math_test.go`:

```go
package math

import "testing"

func TestAdd(t *testing.T) {
    result := Add(2, 3)
    want := 5

    if result != want {
        t.Errorf("Add(2, 3) = %d; want %d", result, want)
    }
}
```

Running `go test` in a terminal compiles and runs every function starting with `Test` in that package.

## Breaking Down the Test Function

**The `_test.go` file name** — Go automatically recognizes files ending in `_test.go` as test files, and excludes them when you `go build` a regular program.

**`func TestAdd(t *testing.T)`** — a test function's name **must** start with `Test` (capitalized), followed by the parameter `t *testing.T` — an object that provides methods for reporting failures.

**`t.Errorf(...)`** — reports a **failed** test, but lets other tests in the same file keep running. Its formatting works just like `fmt.Printf`.

**`t.Fatalf(...)`** — similar to `Errorf`, but stops that test function immediately (used when continuing the test no longer makes sense, for example after a fatal error like a failed connection).

If neither `t.Errorf` nor `t.Fatalf` gets called, the test is automatically considered **passing** — Go doesn't need you to write an explicit "assert success."

## Table-Driven Tests — The Most Idiomatic Pattern

Rather than writing a separate test function for every scenario, the Go idiom is a **table-driven test**: a single slice holding many test cases, run in one loop.

```go
package math

import "testing"

func TestAdd(t *testing.T) {
    cases := []struct {
        name string
        a, b int
        want int
    }{
        {"two positives", 2, 3, 5},
        {"with zero", 0, 5, 5},
        {"two negatives", -2, -3, -5},
    }

    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            result := Add(c.a, c.b)
            if result != c.want {
                t.Errorf("Add(%d, %d) = %d; want %d", c.a, c.b, result, c.want)
            }
        })
    }
}
```

## Breaking Down the Table-Driven Test

**`cases := []struct{ ... }{ ... }`** — a slice of anonymous structs, each representing one test scenario: a descriptive name, inputs (`a`, `b`), and the expected result (`want`).

**`for _, c := range cases`** — a regular loop (from Unit 3!) running each case one at a time.

**`t.Run(c.name, func(t *testing.T) { ... })`** — runs a **subtest** named `c.name`. If one of the cases fails, `go test` shows exactly which subtest failed (e.g. `TestAdd/two_negatives`), not just a generic "TestAdd failed" with no details.

:::tip
Adding a new test case to this pattern just takes one new line in the `cases` slice — no need to write a whole new test function. This is exactly why this pattern is so popular in the Go community.
:::

## Common Mistakes

1. **Forgetting the `Test` prefix on the function name:**
   ```go
   func Add2Numbers(t *testing.T) { ... }  // ERROR: not recognized as a test, go test silently skips it
   ```
   Go **doesn't give an error** for this — the function is just quietly skipped, making you think everything passed when that test never actually ran.

2. **Calling `t.Fatalf` from a separate goroutine:**
   ```go
   go func() {
       t.Fatalf("failed")  // DANGEROUS: t.Fatal must be called from the same goroutine as the test
   }()
   ```
   `t.Fatal`/`t.FailNow` can only be called from the test's main goroutine — this ties back to the concurrency you learned in Unit 7.

## Summary

| Concept | Description |
|---|---|
| Test file | Ends in `_test.go`, separate from regular code |
| Test function name | Starts with capitalized `Test`, parameter `t *testing.T` |
| Marking failure | `t.Errorf(...)` (continues) or `t.Fatalf(...)` (stops) |
| Table-driven test | Slice of test cases + loop + `t.Run` |
